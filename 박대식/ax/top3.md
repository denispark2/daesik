## 1. SRT 자동예매프로그램

목표: 원하는 조건(구간·날짜·시간대·인원·좌석)을 넣어 두면 빈 좌석을 찾아 **결제까지 끝낸 예매확정** 상태로 만들기.

### 1-1. 최종 예매확정까지 단계별 실현 방법

| 단계 | 할 일 | 실현 방법 | 자동화 가능 여부 |
|---|---|---|---|
| 0 | 조건 입력 | 출발·도착역, 날짜, 시간대(예: 18~20시), 인원, 일반/특실, 최대 대기 시간 | 가능 |
| 1 | 로그인 | 회원번호·전화번호·이메일 + 비밀번호. 파이썬 라이브러리 `SRTrain`(ryanking13/SRT, 비공식)이 로그인 지원 | 가능 (비밀번호 보관 문제 → 병목 4) |
| 2 | 접속 대기열 통과 | 명절·주말에는 접속 대기열이 걸림 | 일부. 대기열·보안조치를 **우회하면 부정구매** 소지 (병목 2) |
| 3 | 열차 조회 반복 | 조건에 맞는 열차를 일정 간격으로 조회 → 취소표가 나오는지 확인 | 가능 (`SRTrain` 검색 기능). 조회 간격이 짧으면 차단 위험 (병목 3) |
| 4 | 좌석 예약(홀드) | 빈 좌석이 보이면 바로 예약 → 결제 대기 상태가 됨 | 가능 (`SRTrain` 예약 기능) |
| 5 | 알림 | 예약 성공 시 텔레그램·카카오톡·문자로 "결제하세요 + 결제 기한" 알림 | 가능 |
| 6 | **결제 → 예매확정** | SRT 앱·홈페이지에서 결제해야 승차권 발권(확정) | **사실상 불가.** `SRTrain`은 결제 미지원 (병목 1) |
| 7 | 확정 확인 | 승차권 조회로 발권 확인. 결제 기한을 넘기면 예약 자동 취소 → 3단계로 돌아가 다시 찾음 | 가능 |

**현실적인 구성 (제안)**: 0~5·7단계는 자동, 6단계 결제만 사람이 알림 받고 1탭으로 끝냄.
"완전 자동 확정"이 아니라 **"좌석 확보까지 자동 + 결제는 사람"**.

### 1-2. 병목 · 페인포인트

| # | 병목 | 내용 | 영향 |
|---|---|---|---|
| 1 | **결제 자동화** (가장 큼) | 오픈소스 `SRTrain`은 결제를 지원하지 않음. 자동 결제를 하려면 카드번호·비밀번호를 프로그램에 저장해야 하고, 간편결제는 본인인증(지문·비밀번호)이 사람 손에 있음 | 최종 확정 직전에서 막힘. 사람 개입 필요 |
| 2 | **약관 · 법** | SR은 2025년 설에 불법 매크로 의심 회원 9명(6,400만 건 접속)을 경찰에 수사 의뢰. 2026-01 "보안조치 우회 부정구매 금지·벌칙 신설" 철도 관련 개정안 발의 (통과 여부 확인 못 함). 되팔기(암표)는 2025년 철도사업법 개정으로 단속 근거 생김 | 개인용이라도 계정 정지·수사 위험. 서비스로 배포하면 더 큼 |
| 3 | 차단 · 탐지 | 짧은 간격 반복 조회는 매크로로 탐지됨. 조회 간격을 늘리면 취소표를 놓침 | 속도 ↔ 안전 맞바꿈 |
| 4 | 비밀번호 보관 | 로그인을 자동으로 하려면 SRT 비밀번호를 PC·서버에 저장해야 함 | 유출 위험. 남에게 서비스하면 남의 비밀번호를 맡게 됨 |
| 5 | 비공식 API 변경 | `SRTrain`은 SRT 공식 API가 아님. SRT 쪽 주소·방식이 바뀌면 깨짐 (2.0.0 때 API 주소 변경 반영 이력) | 유지보수 부담, 명절 직전에 고장 나면 쓸모 없음 |
| 6 | 결제 기한 안에 사람이 응답해야 함 | 예약 후 결제 기한을 넘기면 자동 취소. 알림을 못 보면 좌석을 잃음. 일반 예매의 결제 기한(예약 후 몇 분)은 공식 안내에서 **확인 못 함** (명절 예매는 결제 기간 별도 공지) | 6단계 실패 → 7단계에서 다시 찾기 반복 |
| 7 | 취소표 타이밍 예측 불가 | 언제 표가 풀릴지 모름 → 오래 켜 둬야 함 (PC 상시 실행·서버 비용) | 운영 비용 |
| 8 | 노쇼 위약금 | SRT는 노쇼 위약금 기준을 강화함 (출발 3시간 전 취소 기준 보도). 자동으로 여러 표를 잡아 두고 버리면 위약금 | 여러 열차 동시 예약 전략 쓰기 어려움 |
| 9 | 기존 서비스와 차별점 | SRT 자체 예약대기 기능, 2025년 KTX·SRT 통합 앱 출시 보도 → "공식 앱으로도 되는데 왜?"에 답해야 함 | AX 아이디어 선정 시 설득력 |

### 1-3. 아이디어 선정용 메모

- 기술 난이도: 낮음~중간 (0~5단계는 오픈소스로 하루 안에 시제품 가능할 것으로 봄 — 직접 만들어 본 것은 아님)
- 막히는 곳: **결제(1)와 약관·법(2)**. 둘 다 기술이 아니라 규칙 문제라 교육 과제로 풀기 어려움
- 그대로 내면 "매크로 프로그램"으로 보일 수 있음 → 선정한다면 **조회 간격을 사람 수준으로 제한 + 결제는 사람**인 "취소표 알림·좌석 확보 비서"로 범위를 줄이는 쪽이 안전 (제안)

### 1-4. 확인 못 함

- 2026-01 발의된 매크로 금지 개정안의 통과·시행 여부 (국회 의안정보시스템에서 확인 필요)

## 2. 당근 관심 매물 가성비 판단 + 구매·가격협의 채팅

목표: 당근에서 관심 있음으로 설정한 항목에 새 글이 올라오면 → 다른 사이트의 새 제품·비슷한 제품 가격과 비교해 **가성비 좋음/나쁨**을 판단 → 좋으면 판매자에게 **구매 희망 또는 가격 협의 채팅을 자동으로 보냄**.

### 2-1. 단계별 실현 방법

| 단계 | 할 일 | 실현 방법 | 자동화 가능 여부 |
|---|---|---|---|
| 0 | 관심 항목 설정 | 키워드(예: "아이패드 에어 5"), 동네, 최대 가격, 꼭 있어야 할 조건(구성품·상태) | 가능. 당근 앱 키워드 알림 목록은 앱 안에 있어서 프로그램에 **따로 다시 입력**해야 함 |
| 1 | 새 글 감지 | 당근 새 글을 주기적으로 확인 | **어려움.** 당근 공개 API 없음 → 웹 화면을 긁어야 함 (병목 1) |
| 2 | 글 내용 정리 | LLM이 제목·본문·사진에서 모델명·용량·상태·구성품·사용 기간·가격을 뽑음 | 가능 (AI가 잘하는 부분) |
| 3 | 새 제품 가격 찾기 | 네이버 쇼핑 검색 API(공식)로 같은 모델 최저가 조회 | 가능. 이미 NAVER API HUB 써 본 경험 있음 |
| 4 | 중고 시세 찾기 | 번개장터·중고나라·당근 비슷한 글 가격 | 어려움. 공식 API 없음 → 1단계와 같은 문제. 당근 자체 시세는 아이폰·갤럭시만 (2025-01 베타) |
| 5 | 가성비 판단 | 새 제품가·중고 시세 대비 % + 상태 감가 → "좋음/보통/나쁨" + 이유 한 줄 + 제안 가격 | 가능 |
| 6 | **채팅 보내기** | 구매 희망("구매 가능할까요?") 또는 가격 협의("○○원 가능할까요?") | **위험.** 자동 발송 = 사용자 대신 메시지 보내기 (병목 2·3) |
| 7 | 결과 관리 | 보낸 채팅·답장·거래 여부 기록 → 판단 기준 보정 | 일부. 답장 읽기도 1단계와 같은 문제 |

**현실적인 구성 (제안)**: 0~5단계 자동 + 6단계는 **채팅 초안까지만 만들고 알림 → 사람이 1탭으로 보냄**. 1번 아이디어(SRT)와 같은 구조: 찾고 판단하는 건 자동, 마지막 행동은 사람.

### 2-2. 병목 · 페인포인트

| # | 병목 | 내용 | 영향 |
|---|---|---|---|
| 1 | **새 글 데이터 수집** (가장 큼) | 당근은 공개 API가 없음. 웹 화면 수집(크롤링)은 화면이 바뀌면 깨지고, 약관에서 막는지 원문 **확인 못 함**. 관심 목록·채팅은 로그인한 앱 안에 있어 밖에서 꺼내기 어려움 | 1·4·7단계가 다 여기에 걸림 |
| 2 | **자동 채팅 = 계정 제재 위험** | 여러 판매자에게 비슷한 메시지를 자동으로 보내면 스팸으로 보일 수 있음. 당근은 사기 등에 최대 5년 계정 제재, 제재 중 당근페이 잔액 인출 불가 보도 (2026-05) | 계정을 잃으면 서비스 자체가 끝남 |
| 3 | 잘못 보낸 채팅 | "구매 희망"을 보냈는데 AI가 모델·상태를 잘못 읽었으면 거절해야 하고 매너온도 등 평판이 떨어질 수 있음. 동시에 여러 개 "살게요"를 보내면 약속을 다 지킬 수 없음 | 사람 확인 없이 보내기 어려운 이유 |
| 4 | 같은 제품 맞추기 | 중고 글은 모델명·연식·용량이 빠지거나 틀림. "아이패드 팔아요"만 있으면 새 제품가와 비교 불가 | 판단 정확도. 모르면 "판단 보류"로 두는 규칙 필요 |
| 5 | 상태 감가 기준 | 새 제품가 대비 몇 %면 싼지는 품목마다 다름(전자제품 vs 가구). 사진 속 흠집·배터리 상태는 글만으로 모름 | 기준표를 품목별로 따로 만들어야 함 |
| 6 | 중고 시세 비교 대상 없음 | 새 제품가만 비교하면 "중고니까 당연히 싸다"로 다 좋음이 나옴. 진짜 기준은 중고 시세인데 그 데이터가 병목 1과 같은 문제 | 가성비 판단의 핵심 근거가 약함 |
| 7 | 너무 싸면 사기 | 시세보다 훨씬 싼 글이 가성비 1등으로 뜸 → 사기 매물일 수 있음 | "너무 쌈 = 주의" 반대 신호 필요 |
| 8 | 속도 경쟁 | 좋은 매물은 금방 팔림. 확인 간격이 길면 놓치고 짧으면 1번 수집 부담·차단 위험 | SRT 병목 3과 같음 |
| 9 | 기존 기능과 차별점 | 당근 키워드 알림(가격 범위 설정은 어렵다는 분석), AI '내 물건 가격 찾기'(2025-07, 판매자용), 중고 통합 검색 앱(꿀모 등) 있음 | "다른 사이트 새 제품가 비교 + 협의 문구"가 차별점인지 설득 필요 |

### 2-3. 아이디어 선정용 메모

- AI가 제일 잘하는 부분(2·5단계: 글 읽고 정리·판단·문구 만들기)이 핵심이라 **AX 과제로는 1번보다 AI 비중이 큼**
- 막히는 곳: 수집(1)과 자동 발송(2·3). 1번 SRT와 마찬가지로 기술보다 플랫폼 규칙 문제
- 범위를 줄인다면 (제안): **"당근 글 링크를 넣으면 가성비 판단 + 협의 채팅 초안"** — 수집을 사람이 링크 붙여넣기로 대신하면 병목 1·2·8이 사라지고, 2·3·5단계만으로 시제품 가능
- 취업 연결 (제안): 판매 글 정리 → 시장가 비교 → 협상가 제안 흐름은 제조·유통사 **구매(조달) 업무의 견적 비교·단가 협상**과 같은 구조라 SCM 경력과 엮어 설명할 수 있음

### 2-4. 확인 못 함
- 당근 이용약관에 자동화 프로그램·크롤링 금지 조항이 있는지 (원문 확인 필요: daangn.com 약관 페이지)
- 당근 키워드 알림의 현재 설정 범위 (가격 범위 설정 가능 여부)
- 번개장터·중고나라 공식 API 여부
- 네이버 쇼핑 검색 API 일일 호출 한도 (검색에서 숫자 확인 못 함)

## 3. 날씨·운동 기록·일정 기반 주간 운동 계획 (수영·헬스·러닝)

목표: 수영·헬스·러닝을 병행하는 사람에게 **날씨 예보 + 지난 운동 기록 + 직접 입력한 일정**을 보고 이번 주에 언제 어떤 운동을 할지 주간 계획을 짜 줌. 날씨·일정이 바뀌면 남은 날을 다시 짬.

### 3-1. 단계별 실현 방법

| 단계 | 할 일 | 실현 방법 | 자동화 가능 여부 |
|---|---|---|---|
| 0 | 기본 설정 | 운동별 주 목표 횟수(예: 수영 2·헬스 3·러닝 2), 운동 가능한 시간대, 수영장 자유수영 시간·휴관일, 실내 대체 가능 여부(러닝 → 트레드밀) | 사람이 한 번 입력. 수영장 시간표는 시설마다 달라 직접 입력 |
| 1 | 일정 입력 | 이번 주 바쁜 날·약속. 직접 입력 또는 구글 캘린더 연동 | 가능 |
| 2 | 날씨 가져오기 | 기상청 단기예보(며칠 앞, 시간 단위)·중기예보(3~10일) API — 공공데이터포털 무료. 미세먼지는 에어코리아 API | 가능 (공식 API) |
| 3 | 운동 기록 가져오기 | Strava API(공식, 호출 한도 있음) / 기록 앱 CSV 내보내기 / 직접 입력 | 일부. 쓰는 기록 앱에 따라 다름 (병목 1) |
| 4 | 부하·회복 계산 | 운동마다 시간 × 힘든 정도(1~10) = 같은 단위 점수로 맞춤. 같은 부위 연속(헬스 하체 다음날 러닝) 피하기, 주간 증가 폭 제한 | 가능 |
| 5 | 주간 계획 만들기 | 규칙(날씨 → 실외/실내, 일정 → 가능한 날, 부하 → 강도)으로 배치 + LLM이 이유 한 줄 ("목 비 예보 → 러닝을 수로 당김") | 가능 |
| 6 | 알림·조정 | 전날 저녁 "내일 07시 러닝 5km" 알림. 예보·일정이 바뀌면 남은 날만 다시 짬 | 가능 |
| 7 | 했는지 기록 | 했음/못함/바꿈 1탭 → 다음 주 계획에 반영 | 가능 |

**현실적인 구성 (제안)**: 전부 자동화 가능. 3단계만 처음엔 **직접 입력 또는 CSV**로 시작하고, 쓰는 앱이 Strava면 연동.

### 3-2. 병목 · 페인포인트

| # | 병목 | 내용 | 영향 |
|---|---|---|---|
| 1 | **운동 기록 연동** (가장 큼) | 기록이 앱마다 흩어짐. Strava는 공식 API가 있지만 앱별 호출 한도·승인제. Garmin은 개발자 프로그램 승인제이고 2026년 봄부터 신규 신청이 멈췄다는 보도(2026-09, 2차 출처 1건). 애플 건강은 웹 API 없이 아이폰 앱 안에서만 읽음. 헬스 세트·중량은 앱에 없는 경우가 많아 직접 입력 | 자동으로 못 가져오면 매번 입력 → 귀찮아서 안 씀 |
| 2 | 운동끼리 비교 기준 | 수영(m)·헬스(세트·중량)·러닝(km·페이스)은 단위가 다름 → "이번 주 많이 했나"를 하나로 셈하기 어려움 | 시간 × 힘든 정도 점수로 맞추는 방법이 있지만 힘든 정도는 사람이 입력해야 함 |
| 3 | 주간 계획 vs 예보 정확도 | 주간 계획은 월요일에 짜는데, 시간 단위 예보는 며칠 앞까지만 있고 그 뒤는 오전·오후·하루 단위(중기예보) | 주 후반 계획은 자주 바뀜 → 매일 다시 짜기 필요 |
| 4 | 날씨 기준 정하기 | 비·기온·체감온도·미세먼지·폭염 중 무엇을 기준으로 실외 러닝을 뺄지 사람마다 다름 | 처음엔 기준표를 사용자가 정해야 함 |
| 5 | 수영장 제약 | 자유수영 시간·휴관일·강습 일정은 시설마다 다르고 API 없음 | 직접 입력·변경 관리 |
| 6 | 일정 입력 부담 | 일정이 자주 바뀌면 입력을 안 하게 됨 | 캘린더 연동 안 하면 계획이 현실과 어긋남 |
| 7 | 건강·부상 판단 한계 | 통증·피로·컨디션은 기록에 없음. 과훈련·부상 판단은 의료 영역이라 단정 못 함 | "아프면 쉬기" 입력 칸 + 의료 조언 아님 안내 필요 |
| 8 | 계획을 안 지키면 | 못 한 운동을 다음 날로 몰면 부하가 몰림 | 밀린 운동은 버릴지 옮길지 규칙 필요 |
| 9 | 기존 서비스와 차별점 | 러닝·트라이애슬론 AI 코치 앱이 이미 있음 (3-6) | "수영·헬스·러닝 섞기 + 한국 날씨·미세먼지 + 내 일정"을 한 번에 하는 게 차별점인지 확인 필요 |

### 3-3. 아이디어 선정용 메모

- 3개 중 **플랫폼 규칙에 막히는 곳이 가장 적음**: 날씨는 공식 무료 API, 계획은 내 데이터. 1·2번처럼 약관·계정 제재 위험이 없음
- 끝까지 자동으로 갈 수 있는 유일한 아이디어 (1번은 결제, 2번은 채팅 발송에서 사람이 필요)
- 직접 매일 써 보면서 고칠 수 있음 → 교육 기간 안에 시제품 + 실제 사용 기록까지 만들 수 있음
- 약점: 날씨·일정·자원(시간·수영장)을 보고 계획을 다시 짜는 구조는 SCM의 **수요·공급 계획(주간 생산·배송 계획 재조정)**과 비슷하지만, 산업(제조·유통)과 직접 연결은 1~3번 중 2번(구매 단가 비교)이 더 가까움 (제안)

### 3-8. 확장 기능 (제안) — 수면·체성분·회복 데이터로 코칭
- 아이디어: 갤럭시 워치가 재는 수면(단계)·체성분(골격근량·체지방·기초대사량)·HRV·안정 심박을 보고, 정해 둔 루틴 안에서 강도·순서를 조언
  - 예: 수면 5시간 미만·HRV 평소보다 낮음 → 그날 하체·인터벌 대신 상체·가벼운 러닝
  - 예: 골격근량 4주 정체 → 헬스 부위·강도 조정 제안. 체지방 목표 대비 → 러닝·수영 시간 제안
- 데이터 구하기: 삼성헬스 내보내기 CSV에 이미 있음 (weight: 골격근량·체지방·기초대사량·내장지방, sleep_stage, hrv, vitality_score). 앱이면 Health Connect의 수면·체중·체지방·제지방·기초대사량·HRV·안정 심박 기록으로 읽음
- 확인 못 함: 삼성헬스가 Health Connect로 넘기는 항목 범위 (골격근량은 Health Connect에 항목이 없는 것으로 앎), 삼성 자체 SDK 사용 조건
- 주의: 운동 조언까지만. 건강 판단·진단은 안 함. 워치 체성분(BIA) 측정은 오차가 있어 4주 이상 추세로만 봄
- **결정 (2026-11-26 박대식)**: 삼성 자체 SDK가 필요한 기능은 보류. Health Connect로 읽히는 데이터만 씀 (골격근량 등 Health Connect에 없는 항목은 보류) → 삼성 파트너 신청·비용 없음

### 3-10. 확장 기능 (제안) — 마라톤 대회 맞춤 루틴
- 입력: 대회 날짜·종목(5km·10km·하프·풀)·목표 기록. 지금 실력은 러닝 기록(최근 페이스·거리·횟수)으로 자동 판단
- 계획 방식: 대회까지 남은 주를 기초 → 강화 → 최고점 → 줄이기(테이퍼, 대회 전 1~3주)로 나눔. 주마다 장거리 1회를 조금씩 늘리고 주간 거리를 급하게 늘리지 않음
- 다른 운동과 맞추기: 대회가 가까워지면 헬스 하체·강도를 줄이고 수영은 회복용으로. 대회 주에는 하체 없음
- 기존 규칙과 충돌: 비·눈 러닝 금지 때문에 뛸 수 있는 날이 줄어듦 → 예비일을 더 잡음. "러닝 주 1회"는 대회 준비 중엔 주 3회 안팎이 필요
- 가능 여부 판단: 남은 기간이 짧으면 "목표를 10km로 낮추거나 다음 대회 추천"처럼 미리 알려줌
- 대회 일정 자동 가져오기는 보류 (대회 사이트 수집은 약관·사이트 변경 문제) → 사용자가 직접 입력
- 주의: 운동 계획 조언까지만. 부상·통증은 판단 안 함

- **차별점 후보 (제안)**: 갤럭시 워치·삼성헬스 사용자 + 한국 날씨(비·눈·영하) + 수영장 운영시간·강습 고정 + 헬스 부위 규칙을 한 번에 → 해외 지구력 앱이 잘 안 다루는 부분
